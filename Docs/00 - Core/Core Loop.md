The Core Loop describes how Human Drift turns human intention and  
observed reality into understanding and adaptation.

It is **not the same thing as the Domain Model**.

The Domain Model describes what exists: **Journey → Node → Session →  
SessionEntry + Condition**

The Core Loop describes what the product does over time.

---

## Product Loop

```
Intention
   ↓
Understanding
   ↓
Plan / Support Model
   ↓
Approval / Permission
   ↓
Context Detection
   ↓
Events / SessionEntries
   ↓
Autonomous or Assisted Actions
   ↓
Historical Log
   ↓
Analysis / Learning
   ↓
Completion / Adaptation
   ↺
```

The loop is not necessarily linear in real life. Context changes,  
discoveries, revisions, and interruptions can occur at any point. The  
system must preserve that reality rather than forcing it into a clean  
sequence.

## 1. Intention

The person expresses something that matters.

The original intention is preserved. A change in direction does not  
rewrite the original declaration.

## 2. Understanding

The system builds a model of what the person means and what conditions  
matter.

Understanding may include: - desired outcome; - duration; - context; -  
constraints; - success definition; - relevant Nodes; - signals that may  
indicate drift.

Understanding is allowed to remain uncertain.

## 3. Plan / Support Model

The system determines how it can support the intention.

This may include: - what to observe; - what events to record; - what  
context matters; - what actions may be useful.

A plan is a support mechanism, not a rigid requirement that reality must  
obey.

## 4. Approval / Permission

The person approves actions that require authority.

Permission should be explicit where autonomy affects the person's work,  
communication, data, or commitments.

## 5. Context Detection

The system observes relevant signals and conditions.

Context should be understood before intervention.

A detected signal is not automatically a conclusion.

## 6. Events / SessionEntries

Reality is recorded as events.

Within the current domain model, SessionEntries capture what happened  
during a Session, while the Event Log preserves mutations historically.

Events are evidence, not interpretations.

## 7. Autonomous or Assisted Actions

The system may act when sufficient context, confidence, and permission  
exist.

Every autonomous action should be explainable and auditable.

## 8. Historical Log

Events and actions remain available for reconstruction and audit.

Corrections do not erase the original.

## 9. Analysis / Learning

The system compares intention with observed reality and looks for  
meaningful patterns.

This is where drift can be derived.

A single missed action is not automatically drift. The system needs  
enough evidence and context to distinguish: - ordinary variation; -  
temporary interruption; - intentional change; - meaningful drift.

## 10. Completion / Adaptation

A Journey, Node, or Session may reach an end state, but the historical  
record remains.

Completion can lead to: - learning; - changed intention; - a new Node; -  
a new Journey; - or a future continuation.

## Classification Test

When a new idea appears, first classify it:

What it is Where it belongs

---

Real-life observation User Journey / Research  
Product behavior Product Requirements / User Journey  
Domain entity or relationship Domain Model  
Context signal Context Detection  
Historical mutation Event Schema / Event Log  
Autonomous behavior Product + Architecture  
Trust/authority rule Permission Model  
Derived calculation Product / Intelligence  
Fundamental belief Vision & Philosophy / Product Principles  
Implementation work Development

Do not turn every observation into a feature.

Do not use the Core Loop to override the Domain Model.
